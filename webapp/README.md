# Reflex Guard — Real-Time Dashboard

The judge-facing dashboard: a real browser webcam feed, a live simulated
device (no hardware required to run this), and a WebSocket layer that
broadcasts one shared state to every connected browser. This is separate
from `../src/`, which is the Python/OpenCV edge pipeline meant to run on
real camera + STM32 hardware later — this dashboard is the interactive
demo/judging surface.

## Run it

```bash
cd webapp
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python server.py
```

Open `http://localhost:5001`. Open it in a second tab (or a second
computer on the same network, using your machine's IP) — both will show
the exact same live state, because state lives on the server, not in
the browser.

## What's real vs. simulated

| Piece | Real or simulated? |
|---|---|
| Camera feed (Live Camera tab) | **Real** — captured via `getUserMedia`, stays local to your browser, never sent to the server |
| Camera FPS chart | **Real** — measured client-side from actual video frame timing |
| Danger zone | **Real** — you draw it on your own video; saved to `localStorage` |
| AI Vision confidence / latency | **Simulated** — a live random-walk, not a fixed number, generated by `simulation_provider.py` |
| Safety event sequence (hand → danger → relay → power cut) | **Simulated, but the timestamps and elapsed-time response are real** — each step is separated by an actual `time.sleep()` and the "response time" shown in the event log is a genuine measured difference between real timestamps, not a fabricated figure |
| AI Model card (model name, NPU %, backend) | **Labeled honestly** — `aiModel.real` is `false` in simulation mode and the dashboard shows a "SIMULATED TELEMETRY" tag; only `src/vision/qai_hub_model.py` running on real hardware sets it `true` |
| Digital Twin tab | **Twin logic is real** (`src/digital_twin/twin.py` — a real predicted-vs-measured drift model), fed by a modeled hardware-class response time in simulation mode (nominal budget + jitter + an occasional injected slow-relay spike) rather than the Python demo-pacing timer, so the ANOMALY path is something you can actually trigger and watch get caught, not a fabricated "AI-powered" gauge |
| "LIVE HARDWARE" mode | **Honestly non-functional right now** — switching to it will show "HARDWARE NOT CONNECTED" unless `REFLEX_HW_ENDPOINT` points at a real reachable device. It never fakes a connection. |

## Architecture

```
Browser A ─┐
Browser B ─┼── Socket.IO (WebSocket, falls back to polling) ── server.py
Browser C ─┘                                                      │
                                                          active DataProvider
                                                        ┌──────────┴──────────┐
                                                SimulationProvider     HardwareProvider
                                                (default, always on)   (stub — see below)
```

- `simulation_provider.py` — the virtual device: random-walk telemetry
  ticking at 5 Hz, plus a real timed state-machine sequence when a safety
  event fires, plus a live `DigitalTwin` instance (`src/digital_twin/twin.py`)
  fed on every tick and every safety event
- `hardware_provider.py` — the seam for the real Arduino UNO Q / STM32
  system. Implements the exact same interface (`state`, `handle_command()`,
  `tick()`) so the dashboard code never changes when you plug in real
  hardware — only this file does. Also owns its own `DigitalTwin`, so twin
  drift detection works identically once real telemetry is flowing.
- `server.py` — Flask + Flask-SocketIO. Broadcasts state to every
  connected client, persists the event log to `data/events.json`
- `static/js/app.js` — all frontend logic: camera capture, danger-zone
  editor, canvas charts, event table + CSV export, terminal-style system
  log, command buttons, the AI-model NPU gauge, and the digital-twin SVG
  panel

## AI model + digital twin

Both providers publish two extra pieces of state that the dashboard
renders on the Overview and Digital Twin tabs:

- `aiModel` — model name/source (Qualcomm AI Hub's `mediapipe_hand`),
  quantization, backend (`QNN · Hexagon NPU` vs `ONNX Runtime (CPU)`),
  live NPU utilization %, and a `real` flag the UI uses to honestly tag
  the reading as real inference or simulated telemetry.
- `twin` — a `DigitalTwin.snapshot()`: predicted response time (from the
  component latency budget), the last real measured response, the drift,
  and a `NOMINAL` / `DEGRADED` / `ANOMALY` health verdict. See
  `src/digital_twin/twin.py` for where the budget numbers come from and
  what the thresholds mean.

The real (non-simulated) version of `aiModel` and the on-device inference
loop live in `src/vision/qai_hub_model.py` — see the root `README.md` and
`docs/architecture.md` for that side of the pipeline.

## Message format (for connecting real hardware later)

**Client → server**, event `"command"`:
```json
{"action": "trigger_safety_event"}
{"action": "set_tool", "value": "on"}
{"action": "inject_fault", "target": "ai"}
```

**Server → client**, event `"state_update"`:
```json
{
  "mode": "simulation",
  "hardwareConnected": true,
  "system": {"state": "SAFE", "running": true},
  "ai": {"connected": true, "state": "MONITORING", "confidence": 61.2, "latencyMs": 8.4},
  "safety": {"state": "ARMED", "heartbeat": "10:47:38.698"},
  "relay": {"state": "CLOSED"},
  "tool": {"power": "ON"},
  "uptimeSeconds": 12.4,
  "faults": {"ai": false, "camera": false, "stm32": false, "relay": false, "comm": false}
}
```

**Server → client**, event `"event_log"`: one event-log row per safety
transition, with a real timestamp and (where applicable) a real elapsed
response time.

## PC LIVE mode (Snapdragon PC + Arduino UNO Q, real hardware)

The third data-source option — **PC + UNO Q** — is the actual Snapdragon-AI-Lab
architecture: real AI inference on this machine's NPU/CPU, talking over a
real USB-serial link to a real STM32U585 core, not a simulation.

- `pc_provider.py` opens this PC's webcam, runs `AIHubHandDetector` (the
  real Qualcomm AI Hub model from `src/vision/qai_hub_model.py`) on every
  frame, and sends the resulting danger flag to the UNO Q over
  `src/pc_bridge/serial_link.py`.
- `firmware/reflex_guard.ino` is the sketch that runs on the UNO Q's
  STM32U585 core — a small serial protocol with a watchdog, so the relay
  fails safe (power off) if the PC side ever stops responding in time.
- **No board on your desk yet?** Leave `REFLEX_SERIAL_PORT` unset and
  `build_serial_link()` automatically falls back to `MockSerialLink`,
  which implements the identical timing contract (a genuine measured
  round-trip, just over an in-process mock instead of real USB) — so the
  whole pipeline (camera → real AI model → serial protocol → digital
  twin) is testable today, and switching to the real board later is a
  one-line env var, not a code change.
- Requires the optional deps in `requirements.txt` (`opencv-python`,
  `onnxruntime`, `pyserial`). Without them, the server still runs fine
  with just Simulation + Live Hardware modes, and prints a note.

```bash
# with a real UNO Q plugged in:
export REFLEX_SERIAL_PORT=/dev/ttyACM0   # or COM5 on Windows
export REFLEX_CAMERA_INDEX=0
python server.py
# then click "PC + UNO Q" in the dashboard's data source selector,
# then "Start System" on the Simulation Control tab.

# without hardware (mock link, still real AI + real webcam):
python server.py
```

## Connecting real hardware later

1. Set `REFLEX_HW_ENDPOINT=<host>:<port>` before running `server.py`.
2. In `hardware_provider.py`, implement `_try_connect()` to open a real
   WebSocket/serial session to the UNO Q, and `_read_telemetry()` to map
   its messages into the state shape above.
3. Switch `handle_command()` to forward commands to the device instead of
   no-op logging.
4. On the dashboard, click **LIVE HARDWARE** in the data source selector.

No frontend changes are needed — the UI only ever consumes the shared
state shape, regardless of which provider produced it.

## Known limitation

The bundled Flask development server negotiates Socket.IO's WebSocket
upgrade unreliably in some sandboxed/proxied environments (it will still
work over long-polling automatically, which is functionally real-time for
this dashboard's ~5 Hz update rate). On a normal machine/network this
upgrades to a real WebSocket connection without any changes needed. For
an actual production deployment, run behind `eventlet` or `gunicorn` with
a proper Socket.IO-compatible worker instead of `python server.py`.

## Safety note

This dashboard **never** controls real mains power. In simulation, "relay
open" and "tool power off" are state variables shown on screen. When real
hardware is connected, the STM32 remains the physical safety authority —
the dashboard only displays and requests, it does not switch anything
itself.
